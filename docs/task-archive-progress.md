# 任务附件后台打包与下载进度

任务跟踪的“打包下载文件”原先将读取附件、生成 ZIP、下载放在一个请求中，沿用了前端 20 秒超时。新流程先创建后台任务，页面每 2 秒查询真实附件处理数，完成后下载已生成的 ZIP。下载单独使用 10 分钟超时，并根据 Content-Length 显示传输进度；普通接口仍保持 20 秒超时。

## 使用行为

- 保留全部历史提交、提交说明及人员信息；目录仍为“员工（工号）/第 N 版”。进度分母包含全部历史版本附件。
- 页面显示准备、排队、打包（已处理 / 总附件数）、下载及完成状态。处理较大文件时显示当前文件名。
- 关闭进度窗口停止页面轮询和下载请求，后台打包继续；在同一员工进度窗口再次点击可恢复。离开页面后，重新发起会复用该用户正在进行的同一任务打包；已完成 ZIP 只在原组件的重试下载中复用。
- 失败显示具体提示。打包失败可以重新打包；下载失败可使用已完成 ZIP 重试。
- 只有确实不存在的 OSS 对象才生成缺失说明；其他 OSS 错误让打包失败。ZIP 完成前不提供下载，附件尺寸不匹配也会失败，避免返回不完整压缩包。

## 接口

| 方法与路径 | 返回 |
| --- | --- |
| `POST /api/v1/tasks/{taskId}/submission-archives` | 创建或复用进行中的任务，返回 `ApiResponse<Status>` |
| `GET /api/v1/submission-archives/{jobId}` | 当前状态，禁止缓存 |
| `GET /api/v1/submission-archives/{jobId}/download` | 完成后的 ZIP，包含 Content-Length、文件名，禁止缓存 |

`Status` 包括 `jobId`、`taskId`、`state`（QUEUED / RUNNING / READY / FAILED）、`totalFiles`、`processedFiles`、`missingFiles`、`currentFile`、`filename`、`size`、`message`、`expiresAt`。附件数量达到分母时仍需完成 ZIP 尾部，前端在 READY 前最多显示 99%。

创建沿用原任务读取权限与员工数据范围；查询和下载额外要求创建人相同、账号安全版本及角色相同，并重新核对任务及原员工集合的当前权限。知道 jobId 不构成访问权限。

## 运行与清理

- 单应用进程中 1 个打包工作线程，最多排队 2 个；缓存最多保留 8 个任务。
- 单任务附件原始总量上限 2 GiB，进行中及完成任务的附件原始总量预算为 4 GiB；开始前检查可用空间，保留至少 256 MiB。
- 默认目录 `${app.preview.cache-root}/task-archives`，可用 `app.archive.cache-root` 覆盖。生产默认落在已有 `/data/preview-cache` 数据盘挂载内，避免 `/tmp` 的 256 MiB 内存文件系统。
- 打包最长 15 分钟；完成或失败后保留 30 分钟，每分钟清理过期临时文件。下载期间保留正在使用的 ZIP；清理失败会继续重试。
- 作业状态保存在应用进程内，不新增数据库表。服务重启后旧任务返回 410 并提示重新打包；启动时清除专用目录内符合 UUID 命名的旧 `.zip` / `.part`。适用于当前单应用实例部署。

## 验证

自动测试覆盖 ZIP 内容及长度、真实处理进度、逐文件关闭、同一用户重复请求、其他管理员拒绝访问、数据范围收缩、缺失说明与存储失败区分、损坏附件拒绝、过期清理、空任务、体积限制和排队限制；前端覆盖轮询、下载进度、超时、重试、取消以及 Blob 错误解析。浏览器使用独立模拟接口验证进度窗口、关闭恢复、失败提示和重试下载；真实生产任务验收另记发布记录。
